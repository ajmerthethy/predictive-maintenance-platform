# Release v1.0 — Pilot Ready

**Release date:** 2026-07-31
**Branch:** `production-refactor`
**Scope:** Completion of the "Pilot Sprint" milestone (GitHub issues #2–#11)

---

## Overview

This release takes the platform from "refactored but only runnable locally" to genuinely pilot-ready: it's live on a public URL, gated behind real authentication, seeded with realistic demo data, and able to take in a new customer's historical sensor data, alert on critical risk by email, and walk a new machine through onboarding — all without anyone touching the API or database directly.

Nothing in this release adds net-new product surface beyond what a first pilot needs. It was scoped deliberately narrowly, per the project's own governing principle at this stage: *"Can a manufacturing company successfully evaluate the platform in a pilot?"* Every item below was verified end-to-end before being marked done — against a disposable database locally, and, for anything with a live surface, against the production deployment itself.

---

## New Features

- **Single-customer authentication** (#5) — the dashboard and every data endpoint are now gated behind a login. JWT-based, single-tier (any valid login can access everything — there's no per-user data scoping in this model). Users are provisioned only via a CLI script; there's no signup flow.
- **CSV bulk upload for historical sensor data** (#6) — upload a spreadsheet of past readings for a machine instead of entering them one at a time. All-or-nothing validation with a per-row error summary on failure; a downloadable template is provided from the same screen.
- **Email alerting on critical alerts** (#7) — the moment a machine crosses into critical failure risk, an email goes out automatically (via Resend) with the machine name, severity, failure probability, recommended action, and a dashboard link.
- **Guided onboarding flow** (#8) — a single page walks through adding a machine, uploading its historical data, and seeing a live health score, ending with a link into the Fleet Overview. This also introduced the platform's first machine-creation UI — previously, machines could only be created directly via the API.
- **Demo-quality polish** (#9, #10, #11) — clearer empty-state messaging across the dashboard, developer-facing prediction JSON hidden by default (opt-in via an env var), and consistent branding/page titles across all pages.
- **Realistic seeded demo data** (#3) — the production database now has five demo machines spanning healthy, warning, and critical risk profiles, with 90 days of sensor history each, so the platform is demo-able immediately rather than starting from an empty dashboard.

## Infrastructure Improvements

- **First public deployment** (#2) — both the backend and dashboard now run continuously on Railway, each auto-deploying on every push to `production-refactor`.
- Both Dockerfiles now bind to Railway's dynamically-assigned `$PORT`, falling back to the original fixed ports (8000/8501) for local `docker-compose` use.
- `dashboard/Dockerfile` was rewritten to build from repo-root context (matching how `backend/Dockerfile` already worked) — Railway's Dockerfile Path setting on this plan has no separate build-context override, so the original subdirectory-context Dockerfile failed to build there.
- `bcrypt` pinned to `4.0.1` — `bcrypt` 5.x removed an attribute `passlib` 1.7.4 depends on for its version check, which broke every password hash/verify call in a way that only surfaced at runtime, not at install time.

---

## Database Changes

No new Alembic migrations were introduced in this release — the auth feature reuses the `users` table (migration `a7e51dff993f`), which was created during the prior refactor phase and had gone unused until now.

The only database change in this release is operational: the production Supabase database was seeded via `backend/scripts/seed_database.py` with 5 machines, ~2,160 sensor readings per machine, matching predictions, and one active critical alert.

## Security

- Authentication is real and enforced for the vast majority of the API — verified live: a request without a token to a protected route returns `401`; a valid login returns a usable JWT; `/health` and `/auth/login` remain intentionally open.
- Passwords are hashed with bcrypt via `passlib`; there is no plaintext password storage anywhere in the system.
- **Known gap, not yet fixed in this release:** `GET /machines/{id}/health` and `GET /machines/{id}/trend` are reachable without a token in production today. These live in a router that was accidentally left out of the authentication wiring in `main.py` because it shares a name with the (correctly public) `/health` liveness check, but it is a different router entirely, containing real per-machine sensor data. This is scheduled to be fixed as the next immediate priority — see the engineering log for detail.
- `JWT_SECRET_KEY` has an insecure hardcoded fallback for local development if the environment variable is unset. It's set correctly in the production environment today, but there's no startup-time check preventing a silent reversion to the fallback.

## Deployment

- **Backend:** `https://predictive-maintenance-platform-production.up.railway.app`
- **Dashboard:** `https://predictive-maintenance-platform-production-523c.up.railway.app`
- Both services deploy from GitHub's `production-refactor` branch — notably **not** the repository's default branch (`main`), which still reflects the pre-refactor MVP. This means GitHub's automatic issue-closing on `Closes #N` commit messages doesn't fire; issues in this sprint were closed manually after verification.
- Required environment variables: `DATABASE_URL` (Supabase), `JWT_SECRET_KEY`, `RESEND_API_KEY`, `EMAIL_ALERT_RECIPIENT` (backend); `API_URL` (dashboard, pointing at the backend's public domain).
- `backend/start.sh` runs `alembic upgrade head` before starting the server on every deploy, so schema migrations apply automatically.

## Performance

No dedicated performance work was done as part of this specific sprint — the scope was deliberately about pilot-readiness (auth, deployment, data ingestion, alerting), not optimization. Two relevant improvements from the immediately preceding refactor work are already part of this release's baseline: N+1 query fixes in the risk/analytics query paths, and pagination on list endpoints. No load testing or performance benchmarking has been done against the production deployment at any point.

## Known Limitations

- **Single customer only.** One login, no multi-tenancy, no per-user data scoping — by design for this stage, not an oversight.
- **No live sensor integration.** Historical data comes in via CSV upload; there's no real-time IoT/OPC-UA/historian connection yet.
- **Email alerting can't yet reach a real customer's inbox.** Resend is configured with its sandbox sender (`onboarding@resend.dev`), which can only deliver to the Resend account owner's own address until a domain is verified.
- **The `health.router` authentication gap** described above is live in production as of this release.
- **No automated regression tests for the authentication flow itself**, or for the dashboard — both were verified manually and via ad hoc test scripts during this sprint, not committed as an ongoing test suite.
- **No rate limiting** on the login endpoint.
- **No external uptime or error monitoring** on the deployed services — only the in-app email alerting for ML predictions exists today; an actual backend outage would not notify anyone.

## Upgrade Notes

For anyone standing up this release fresh, or bringing an existing local/staging environment up to date with it:

1. **New backend dependencies** — `pyjwt`, `passlib[bcrypt]`, `bcrypt==4.0.1` (not 5.x), `requests`, `python-multipart`. Run `pip install -r backend/requirements.txt`.
2. **New required environment variables** — `JWT_SECRET_KEY` (generate a real random value; do not rely on the insecure dev default), `RESEND_API_KEY` and `EMAIL_ALERT_RECIPIENT` if email alerting is wanted, `API_URL` on the dashboard side pointing at the backend's actual address.
3. **Provision at least one login user** — there's no signup flow. Run `python backend/scripts/create_user.py <username> <email> <password>` against the target database before attempting to log in.
4. **No new migrations to run** beyond what was already required by the prior refactor — `alembic upgrade head` as usual is sufficient (and happens automatically on Railway via `start.sh`).
5. **If deploying to Railway specifically**, double-check the public domain's target port after generating it — it has been observed defaulting to an incorrect value (`1`) even when the app is healthy internally, which manifests as a `502 Application failed to respond` from Railway's edge, not from the app itself.
